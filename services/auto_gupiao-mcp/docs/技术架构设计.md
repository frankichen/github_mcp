# 技术架构设计

## 1. 架构目标

本系统采用 Go Modules 构建，优先保证核心策略逻辑可测试、可回测、可替换。实盘接入前，所有交易动作必须先经过回测和模拟盘验证。

## 2. 分层设计

- `cmd/autogupiao`：命令行入口，负责参数解析和流程触发。
- `internal/domain`：领域模型，包括股票快照、候选股、交易成本、整手计算。
- `internal/data`：数据输入适配层，当前支持 CSV，后续可扩展行情接口。
- `internal/selector`：股票评分、排序和候选股筛选。
- `broker`（规划）：券商或模拟盘适配器。
- `backtest`（规划）：历史回测、撮合、成本计算和绩效指标。
- `scheduler`（规划）：14:00 后选股、次日 10:00 卖出等定时任务。
- `report`（规划）：候选股、交易、收益、风控拦截报表。

## 3. 核心流程

1. 拉取或导入日内行情快照。
2. 标准化股票字段和交易状态。
3. 剔除停牌、ST、涨跌停、不可买入标的。
4. 按资金、整手和成本模型计算可买数量。
5. 根据趋势、量能、动量、估值、基本面质量生成评分。
6. 按评分和风险等级排序，输出候选股。
7. 模拟盘或实盘阶段由交易执行模块生成委托。
8. 次交易日按卖出策略执行退出。

## 4. 数据接口规划

行情数据接口需要返回：

- 股票代码、名称、市场。
- 最新价、昨收、最高、最低、涨跌幅。
- 成交额、换手率、量比。
- 均线、RSI、短期涨幅等技术指标。
- 停牌、ST、涨跌停状态。
- 基本面指标：ROE、营收增速、净利增速、资产负债率、PB。

后续建议实现统一接口：

```go
type MarketDataProvider interface {
    ListSnapshots(ctx context.Context, tradingDay string) ([]domain.StockSnapshot, error)
}
```

## 5. 交易接口规划

交易接口必须通过适配器隔离，不允许策略层直接调用券商 SDK。

```go
type Broker interface {
    Cash(ctx context.Context) (float64, error)
    Positions(ctx context.Context) ([]Position, error)
    Buy(ctx context.Context, order Order) (OrderResult, error)
    Sell(ctx context.Context, order Order) (OrderResult, error)
}
```

实盘前必须保留：

- dry-run 模式。
- 人工确认开关。
- 单日亏损熔断。
- 接口失败不下单。
- 委托和成交全链路审计。

## 6. 配置原则

策略参数、资金参数、成本参数、风控参数都应配置化。当前 `configs/example.yaml` 是配置草案，后续应接入配置解析模块。

## 7. 测试策略

- 领域模型：测试整手计算、成本计算、可交易过滤。
- 评分器：测试趋势标的高分、过热标的降分、不可交易标的剔除。
- 数据层：测试字段缺失、类型错误、空文件、异常 CSV。
- 回测层：测试成交、持仓、收益、最大回撤。
- 交易层：全部使用 mock broker 做单元测试。
